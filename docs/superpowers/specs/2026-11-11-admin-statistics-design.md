# 管理端数据统计与学生账号查看设计

## 背景

管理端已经具备院校、专业、录取记录和批量导入能力，但管理员缺少整体数据视图。系统需要在同一页面查看基础数据规模、院校分布、录取趋势、收藏排行、数据完整度，并分页查看学生账号。

## 目标

- 新增管理员数据统计页面。
- 展示院校、专业、录取记录、学生账号和收藏总量。
- 展示院校层次和地区分布。
- 展示历年录取记录数量、平均最低分和平均最低位次趋势。
- 展示收藏数量最高的院校排行。
- 提示缺少专业或缺少录取记录的院校、专业。
- 分页查看学生账号的非敏感档案字段。
- 所有接口仅允许管理员访问。

## 非目标

- 不新增数据库表结构。
- 不修改院校、专业、录取记录或学生档案。
- 不导出 Excel 或 PDF 报表。
- 不实现实时统计、定时任务、大屏轮播或复杂 BI 组件。
- 不展示学生密码哈希、令牌或其他敏感信息。
- 不把统计结果解释为录取概率或预测结论。

## 反目标

- 不能在前端分别请求大量列表后在浏览器完成全量聚合。
- 不能逐院校查询专业和录取记录，避免 N+1 查询。
- 不能因为某个统计维度为空导致整个页面失败。
- 不能把演示录取数据展示为官方统计结论。
- 不能让学生账号访问统计数据或学生账号列表。

## 方案比较

### 方案一：独立统计聚合接口 + 独立学生分页接口

后端一次返回统计概览，学生账号列表单独分页查询。前端新增 `/admin/statistics` 页面。

优点是统计口径集中、页面请求少、学生分页不会让概览响应膨胀；缺点是后端需要多个轻量查询和服务转换。

### 方案二：所有数据由前端聚合

前端请求院校、专业、录取记录、收藏和学生列表后自行计算。

开发直接，但会传输大量无用数据、分页困难，后续数据增长时不可控，不采用。

### 方案三：逐院校聚合接口

前端遍历院校获取各校详情。

请求数量随院校数增长，容易出现部分失败和统计不一致，不采用。

最终采用方案一。

## 统计接口

```text
GET /api/admin/statistics/overview
权限：ADMIN
```

返回：

```text
AdminStatisticsOverviewVO
├─ universityCount
├─ majorCount
├─ admissionRecordCount
├─ studentCount
├─ favoriteCount
├─ universityLevels[]
│  ├─ label
│  └─ count
├─ universityProvinces[]
│  ├─ label
│  └─ count
├─ admissionTrends[]
│  ├─ year
│  ├─ recordCount
│  ├─ averageMinScore
│  └─ averageMinRank
├─ topFavorites[]
│  ├─ universityId
│  ├─ universityName
│  └─ favoriteCount
└─ dataCompleteness
   ├─ universitiesWithoutMajors
   ├─ universitiesWithoutAdmissions
   └─ majorsWithoutAdmissions
```

统计口径：

- 院校、专业、录取记录和收藏数量来自当前数据库全量。
- 学生数量只统计角色为 `STUDENT` 的账号。
- 地区分布按院校所在省份计数，空省份归为“未填写”。
- 层次分布空值归为“未分类”。
- 年度趋势只统计有最低分或最低位次的录取记录，平均值四舍五入为整数。
- 收藏排行按院校聚合，最多返回 5 所。
- 缺少专业按院校统计；缺少录取记录分别按院校和专业统计。

## 学生账号接口

```text
GET /api/admin/students?page=1&size=10&keyword=
权限：ADMIN
```

查询规则：

- 只返回角色为 `STUDENT` 的账号。
- `keyword` 同时匹配用户名和昵称。
- 按创建时间倒序、编号倒序。
- 返回 `PageResult<StudentVO>`。

`StudentVO`：

```text
id
username
nickname
province
examYear
subjectTrack
score
provinceRank
createdAt
```

不得包含 `passwordHash`。

## 后端实现

- 新增 `AdminStatisticsController`。
- 新增 `AdminStatisticsService` 和实现类。
- 概览一次读取院校、专业、录取记录和收藏列表，并在内存中完成小规模聚合。
- 学生数量和学生分页使用 `UserMapper`，数据库过滤 `STUDENT` 和关键词。
- 收藏排行批量加载相关院校名称，避免逐条查询。
- 空集返回空数组和 0 值，不抛出异常。

## 前端实现

新增 `/admin/statistics` 页面和管理员菜单“数据统计”。

页面结构：

1. 5 个指标卡：院校、专业、录取记录、学生、收藏。
2. 院校层次柱状图。
3. 院校地区分布图。
4. 录取年度趋势组合图：记录数量柱状、平均最低分折线、平均最低位次折线。
5. 收藏院校 Top 5 列表。
6. 数据完整度提示。
7. 学生账号表格、关键词查询和分页。

页面提供加载、空数据、失败重试和刷新状态。图表封装为纯数据转换函数，便于 Vitest 测试。

## 测试

后端服务测试覆盖：

- 指标和空数据。
- 层次、地区和年度趋势聚合。
- 收藏 Top 5 顺序和院校名称。
- 数据完整度计算。
- 学生关键词、角色过滤和分页。
- 学生 VO 不含密码字段。

前端测试覆盖：

- 层次和地区图表数据转换。
- 年度趋势序列和空状态。
- 收藏排行空状态。
- 数据完整度提示文案。

## 验收标准

1. 管理员可以从菜单进入数据统计页面。
2. 5 个总量指标与数据库一致。
3. 层次、地区、年度趋势和收藏排行可以显示。
4. 空数据页面不崩溃。
5. 数据完整度能够指出缺失数据的院校或专业。
6. 学生账号分页和关键词查询可用，且不返回敏感字段。
7. 学生账号访问管理接口时被拒绝。
8. 后端测试、前端测试、生产构建和便携环境验证通过。

## 自检结论

本设计复用现有表结构和 ECharts，不增加外部服务。统计维度适合本科毕业设计展示，数据量较小时后端内存聚合可解释且实现成本适中。
