# 管理端专业与录取记录维护设计

## 背景

学生端已经完成院校查询、院校详情、专业录取趋势、冲稳保筛选和收藏对比。管理端目前只能维护院校基础信息，专业与录取记录只能通过数据库脚本写入，管理员无法在页面上完成日常数据维护。

本阶段补齐管理端“院校数据维护”闭环，使管理员可以在选定院校后维护专业和历年录取记录，并保证新增数据能够被学生端详情和推荐功能直接使用。

## 目标

- 管理员可以查看、筛选、新增、编辑和删除指定院校下的专业。
- 管理员可以查看、筛选、新增、编辑和删除指定院校下的录取记录。
- 每条新增或编辑的录取记录必须绑定当前院校下的具体专业。
- 后端阻止院校归属不一致、重复录取记录和删除仍被引用的专业。
- 专业或录取记录变化后，使推荐缓存失效，避免继续返回旧结果。
- 保持普通本科项目可理解的分层结构，不引入新的复杂框架。

## 非目标

- 不在本阶段实现 CSV 批量导入和错误行反馈。
- 不新增管理员数据统计页面。
- 不修改学生端现有推荐算法、详情展示和收藏规则。
- 不改动现有数据库表结构。
- 不支持通过管理端新增“整校”或“院校专业组”级别录取记录。
- 不实现操作审计日志、软删除和多人并发编辑。

## 反目标

- 不能只在前端隐藏错误选项而缺少后端归属校验。
- 不能让同一专业、年份、省份、科类和批次出现重复录取记录。
- 不能因为专业已被录取记录或收藏引用而直接产生数据库外键异常。
- 不能在修改录取数据后继续使用未失效的推荐缓存。
- 不能把专业、录取记录和院校基础信息塞进一个无法分页维护的超大表单。

## 关键决定

### 录取记录必须绑定专业

管理端新增和编辑录取记录时必须选择具体专业，该专业必须属于 URL 中的院校。

数据库中 `admission_record.major_id` 暂时保留可空定义，用于兼容历史数据；本次不修改表结构。后端维护接口不提供空专业选项。

### 采用嵌套资源接口

接口路径明确包含院校编号：

- `/api/admin/universities/{universityId}/majors`
- `/api/admin/universities/{universityId}/admission-records`

院校归属校验使用路径中的 `universityId`，请求体不接受可覆盖它的院校编号。

### 前端使用一个院校数据维护抽屉

院校列表保留现有维护入口，并新增“数据维护”操作。打开后以当前院校为上下文，在抽屉中使用“专业”和“录取记录”两个页签完成维护，避免增加多个管理菜单。

## 方案比较

### 方案一：嵌套资源接口加单页数据维护抽屉

后端按院校维护专业和录取记录，前端在院校列表中进入数据维护抽屉。

优点是院校归属关系直接体现在接口中，服务层校验清楚；前端操作集中，演示路径短。缺点是 Controller、服务测试和抽屉组件会比现有院校 CRUD 稍多。

### 方案二：独立资源接口加多个管理菜单

使用 `/api/admin/majors` 和 `/api/admin/admission-records`，前端增加两个独立页面。

接口形式简单，但每次请求仍需携带院校编号并重复校验归属，后端菜单和页面数量增加，不符合当前系统规模。

### 方案三：整校聚合保存

一次提交院校、专业列表和录取记录列表，由后端整体保存。

适合数据一次性初始化，不适合逐条编辑、分页查询和后续批量导入。单个请求过大，错误定位困难，因此不采用。

最终采用方案一。

## 数据契约

### 专业接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/universities/{universityId}/majors` | 查询当前院校专业 |
| POST | `/api/admin/universities/{universityId}/majors` | 新增专业 |
| PUT | `/api/admin/universities/{universityId}/majors/{majorId}` | 更新专业 |
| DELETE | `/api/admin/universities/{universityId}/majors/{majorId}` | 删除专业 |

专业查询支持可选 `keyword`，同时匹配专业名称和门类。专业数据较少，本阶段返回列表，不分页。

新增和更新使用 `MajorSaveRequest`：

```text
name                 专业名称，必填
category             专业门类，可选
subjectRequirement   选科要求，可选
description          专业简介，可选
```

返回继续复用 `MajorVO`。

### 录取记录接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/universities/{universityId}/admission-records` | 分页查询录取记录 |
| POST | `/api/admin/universities/{universityId}/admission-records` | 新增录取记录 |
| PUT | `/api/admin/universities/{universityId}/admission-records/{recordId}` | 更新录取记录 |
| DELETE | `/api/admin/universities/{universityId}/admission-records/{recordId}` | 删除录取记录 |

查询参数：

```text
page                 页码，默认 1
size                 每页数量，默认 10，最大 100
majorId              专业编号，可选
year                 录取年份，可选
province             招生省份，可选
subjectTrack         科类或选科组合，可选
```

新增和更新使用 `AdmissionRecordSaveRequest`：

```text
majorId              必填，必须属于当前院校
province             必填
year                 必填，不早于 2000 年且不晚于当前年份
subjectTrack         必填
batch                必填
minScore             必填，0 至 1000
minRank              必填，必须大于 0
planCount            可选，不能小于 0
source               必填
```

返回新增的 `AdminAdmissionRecordVO`，包含记录编号、院校编号、专业编号与名称、年份、省份、科类、批次、最低分、最低位次、计划数和来源。

## 后端实现

新增 `AdminCatalogController`、`AdminCatalogService` 和 `AdminCatalogServiceImpl`，继续使用 Controller、Service、Mapper 分层。

服务层职责：

1. 每次操作先校验院校存在。
2. 新增、更新和删除专业前校验专业属于当前院校。
3. 新增和更新录取记录前校验专业属于当前院校。
4. 对院校、专业、省份、年份、科类和批次执行重复检查。
5. 删除专业前检查录取记录和收藏引用，有引用时返回明确业务提示。
6. 删除院校前检查其下是否仍有专业，避免直接暴露数据库外键错误。
7. 所有会改变推荐输入的写操作清除 `recommendations` 缓存。

字符串字段在保存前去除首尾空格。请求体中的院校归属不可信，统一从路径参数取得。

重复录取记录的判定键为：

```text
universityId + majorId + province + year + subjectTrack + batch
```

更新记录时排除当前记录编号。

## 前端实现

### 院校列表

- 保留现有新增、编辑和删除操作。
- 新增“数据维护”操作，打开当前院校的数据维护抽屉。
- 保留院校关键词查询和分页。

### 数据维护抽屉

抽屉标题展示院校名称和地区，包含两个页签：

#### 专业页签

- 关键词筛选。
- 表格展示专业名称、门类、选科要求和简介。
- 新增和编辑使用同一表单。
- 删除前二次确认。
- 服务端返回“专业已被引用”时保留抽屉，并显示具体错误信息。

#### 录取记录页签

- 支持专业、年份、省份和科类筛选。
- 表格分页展示年份、专业、省份、科类、批次、最低分、最低位次、计划数和来源。
- 新增和编辑使用同一表单。
- 专业选择器只加载当前院校专业。
- 当前院校没有专业时禁止新增录取记录，并提供先新增专业的提示。
- `majorId` 必填，来源默认填入“演示数据（非官方）”，管理员仍可修改。

### 状态处理

- 列表加载时显示加载状态。
- 空列表显示明确空状态。
- 接口失败显示错误信息和重试入口。
- 新增、更新或删除成功后刷新当前页签数据。
- 保存按钮在请求期间防止重复提交。

## 测试计划

### 后端服务测试

- 正常查询指定院校的专业和分页录取记录。
- 院校不存在时返回业务异常。
- 更新或删除不属于当前院校的专业时拒绝操作。
- 新增录取记录时专业必填。
- 专业属于其他院校时拒绝新增录取记录。
- 重复录取记录时拒绝新增，更新当前记录时不误判重复。
- 删除未被引用专业成功。
- 删除已有录取记录或收藏引用的专业时拒绝。
- 正常新增、更新和删除专业与录取记录。

### 前端单元测试

- 录取记录表单正确清理字符串和可选数字字段。
- 筛选条件转换为接口参数时忽略空值。
- 页码和每页数量整理为有效整数。

### 构建与手工验证

- 后端 Maven 测试通过。
- 前端 Vitest 和 Vite 生产构建通过。
- 使用便携环境启动 MySQL、Redis、后端和前端。
- 管理员新增专业后，可以在学生端院校详情中看到该专业。
- 管理员新增录取记录后，可以在学生端趋势图中看到数据。
- 修改录取记录后再次请求推荐，确认旧缓存结果已失效。
- 删除仍有录取记录的专业时，页面显示可理解的业务提示。

## 验收标准

1. 管理员可以在院校列表中进入任一院校的数据维护抽屉。
2. 可以完成专业和录取记录的新增、编辑、删除与筛选。
3. 录取记录只能选择当前院校下的专业。
4. 重复录取记录和跨院校专业关联被后端拒绝。
5. 被录取记录或收藏引用的专业不能删除。
6. 管理端修改后，学生端详情和新推荐结果能够反映最新数据。
7. 加载、空数据、错误和保存中状态完整。
8. 自动化测试、生产构建和便携环境主流程验证通过。

## 自检结论

本设计复用现有表结构和技术栈，管理边界与学生端数据口径一致。没有需要学校模板或外部数据才能决定的问题；具体表格列宽、按钮文案和提示颜色属于实现细节。
